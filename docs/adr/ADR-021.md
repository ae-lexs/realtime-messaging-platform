# ADR-021: Cloud Substrate Migration — GCP, PostgreSQL, and the Data Lake Tap

- **Status**: Accepted
- **Date**: 2026-07-24
- **Supersedes**: ADR-014 (technology stack & deployment); the decision outcomes of ADR-004 (sequencing) and ADR-007 (data model)
- **Amends**: ADR-003 (source of truth & dataflow), ADR-010 (Redis provider), ADR-011 (Kafka provider), ADR-012 (observability backend)

---

## Context and Problem Statement

ADR-014 selected an AWS-native substrate: DynamoDB (authoritative state), MSK Serverless (event log), ElastiCache Redis (ephemeral), ECS Fargate (compute), ALB (ingress), and CloudWatch/X-Ray (observability). It also mandated a local, fully-runnable stack (Docker Compose + LocalStack) as the primary development environment.

Three forces have changed since that decision:

1. **The AWS free tier is exhausted.** The Lambda and Cascade resilience ateliers consumed the account's free-tier allowances. Continued AWS spend on this lab is no longer justified.
2. **A GCP Free Trial credit is available.** The account holds **$5,238 in credit expiring 2026-10-23** — roughly $1,700/month of runway. This removes cost as a binding constraint on managed-service selection, *provided* infrastructure is deployed and destroyed in short windows (hours, not weeks) rather than left running.
3. **Two scope decisions have been reversed by the author.** First, the "one database for everything" constraint that drove the DynamoDB selection in ADR-004 is **lifted** — the sequencing store no longer must equal the entity store, which reopens relational options. Second, the analytics/data-lake tier that ADR-003 and ADR-011 repeatedly deferred as "future" is now **in scope** as a first-class design concern, because whether the event log feeds an analytical sink affects the topic and schema design *now*, not later.

A fourth change follows from (2) and (3): the requirement for a locally-runnable stack is **withdrawn**. The value it provided — fast iteration without cloud spend — is now better served by deploy-to-GCP-then-destroy, and maintaining LocalStack parity for DynamoDB, MSK, and ElastiCache is undifferentiated work that a cloud-native lab need not carry. Development targets a real GCP dev project.

**Core question:** What GCP substrate satisfies the substrate-neutral architectural contracts (ADR-001, ADR-002, ADR-005, ADR-006, ADR-008, ADR-009), best implements the sequencing requirement now that the single-store constraint is lifted, keeps the Kafka event log intact, and adds an analytical data-lake tap — while remaining deployable-and-destroyable within a trial budget?

---

## Decision Drivers

1. **Contract preservation.** The migration must not weaken any invariant in ADR-001–013. Substrate is an implementation detail beneath the contracts; a choice that forces a contract change is disqualified unless the change is an improvement.
2. **Sequencing correctness, simplified.** ADR-004's two-phase design (allocate, then persist non-atomically, tolerating gaps) exists *because* DynamoDB `TransactWriteItems` cannot return the incremented counter value. A substrate that can read-modify-write-and-return in one transaction should be preferred, because it collapses two phases into one and shrinks the gap window.
3. **Keep Kafka.** The event log's partitioning contract (ADR-011) and per-chat ordering dependency (ADR-001) are load-bearing. The substrate must offer the Kafka API, not a semantically different queue.
4. **Data lake as a first-class tap.** The event log must be able to feed an analytical store cheaply and natively, and the topic/schema design must account for a second, analytical consumer from the outset.
5. **Deploy-and-destroy economy.** Every component must be provisionable and destroyable by Terraform in a single short session. Fixed monthly-priced services that assume long-lived operation are penalised relative to their metered cost during a short window.
6. **No local infrastructure.** Development and testing run against GCP. No component may *require* a local emulator to be exercised.
7. **Learning surface.** Where two options are otherwise close, prefer the one that exposes a more interesting distributed-systems problem (this is a lab), provided it does not compromise drivers 1–2.

## Considered Options and Decisions, by Axis

### Axis A — Authoritative datastore (replaces DynamoDB)

The DynamoDB single-table design served two very different jobs: the **ordered message-write path** (sequence + message + idempotency, which demands transactional atomicity) and **entity/document state** (users, chats, memberships, sessions, which are read-mostly documents with no cross-entity transaction requirement). The lifting of the single-store constraint lets these be served by different engines chosen for their access pattern — a deliberate polyglot-persistence split rather than a forced monoculture.

**The hard boundary:** the ordered write path must live in one transactional store, because ADR-004's entire simplification (two phases → one transaction) depends on the sequence allocation, the message insert, and the idempotency-key commit being atomic *together*. Splitting the sequence from the message across two systems would re-introduce the very two-phase cross-system write the migration removes. So the boundary is drawn at the write path, not at conceptual entity lines.

| Store | Owns | Reasoning |
|---|---|---|
| **Cloud SQL for PostgreSQL** (chosen — message & delivery path) | `chat_counters`, `messages`, `idempotency_keys`, `delivery_state` | Native sequences and `UPDATE … RETURNING` inside a transaction collapse ADR-004's two phases into one. Postgres sequence gaps (`nextval` is never rolled back) match ADR-001's "gaps are acceptable" exactly. `delivery_state` lives here deliberately — see below. |
| **Firestore, native mode** (chosen — identity & membership) | `users`, `chats`, `memberships`, `sessions` | Document model fits read-mostly entity data; serverless and **scales to zero**, so it carries no idle cost between deploy-destroy cycles (unlike the Postgres primary). This is the deliberate exploration of a non-relational store for state that does not need cross-entity transactions. Firestore's own real transactions remain available if a future access pattern needs them. |

**`delivery_state` (ADR-008 watermarks) is placed in Postgres, not Firestore — and this is an architectural decision, not a style preference.** The reconnect-sync path compares a watermark against `messages.seq`: `SELECT … FROM messages WHERE chat_id = $1 AND seq > $watermark`. If the watermark lived in Firestore and messages in Postgres, that comparison would straddle two stores with no shared transaction boundary, clock, or failure domain — and the Fanout Plane (a Kafka consumer that advances the watermark and then commits its offset) would couple sync correctness to Firestore write availability rather than to message-store availability. Keeping `delivery_state` beside `messages` puts the watermark and the data it indexes in one failure domain and makes the sync query a single-store read. Re-delivery on a stale watermark remains safe per ADR-009, but its frequency is now governed by the message store's availability, not a second store's. The non-relational exploration is fully satisfied by the identity/membership collections above; `delivery_state` has a concrete consistency reason to stay relational.

**Rejected for the entity tier:** *Bigtable* (wide-column, hourly-billed, no scale-to-zero — overkill for low-volume document state). *MongoDB Atlas* (document model, but an external account/dependency; Firestore is the GCP-native equivalent). **Rejected for the write path:** *Firestore* (a hot per-chat counter hits single-document contention, and the documented remedy — sharded distributed counters — *breaks monotonicity*, the one property we need). *Cloud Spanner* (native sequences but operationally heavy; buys nothing Postgres lacks here). *External sequencer / etcd — ADR-004 Option 3* (raised given the move to Kubernetes). Two independent arguments each suffice to reject it. **Structural (the stronger):** a separate sequencer re-introduces the cross-system atomicity problem — the sequence is allocated in one system and the message persisted in another, which is exactly the two-phase cross-store write a single transactional store eliminates. **Performance:** etcd serves writes only from the Raft leader at RTT + fsync per request, with throughput that *degrades* as transaction size grows — a low-write coordination store, not a high-rate multi-key counter. It would be a more interesting component and a worse architecture.

**Decision A: a polyglot split** — Cloud SQL for PostgreSQL owns the ordered write path; Firestore (native mode) owns entity/document state.

The sequencing mechanism becomes, per chat, a counter row advanced in the same transaction that persists the message. **Idempotency must be checked _before_ a sequence is allocated** — ADR-001/ADR-004 require that a retry with the same `client_message_id` returns the *same* sequence. A naive `INSERT … ON CONFLICT DO NOTHING` at the end of the transaction is wrong: on a retry it silently allocates a *new* sequence and inserts a *duplicate* message while ignoring the key. The DynamoDB two-phase design enforced check-before-allocate; the Postgres design must too. The chosen pattern is a fast-path read outside the transaction plus a concurrency-safe claim inside it:

```sql
-- Fast path (retry): return the ORIGINAL result; no allocation, no write.
SELECT seq, message_id FROM idempotency_keys
  WHERE chat_id = $1 AND client_message_id = $2;
-- If a row is found, return (seq, message_id) and stop.

-- Slow path (first sight of this client_message_id): one transaction.
BEGIN;
  -- Claim the key first. If a concurrent writer already claimed it, zero rows
  -- return -> ROLLBACK, then re-run the fast-path SELECT and return that.
  INSERT INTO idempotency_keys (chat_id, client_message_id)
    VALUES ($1, $2) ON CONFLICT DO NOTHING RETURNING 1;   -- 0 rows => lost the race

  -- Only reached when the key was successfully claimed:
  WITH alloc AS (
    UPDATE chat_counters SET seq = seq + 1 WHERE chat_id = $1 RETURNING seq
  ), ins AS (
    INSERT INTO messages (chat_id, seq, client_message_id, sender_id, body, created_at)
      SELECT $1, alloc.seq, $2, $3, $4, now() FROM alloc
      RETURNING seq, id AS message_id
  )
  UPDATE idempotency_keys k SET seq = ins.seq, message_id = ins.message_id
    FROM ins WHERE k.chat_id = $1 AND k.client_message_id = $2;
COMMIT;
```

**Race and isolation (an explicit part of the contract).** The fast-path `SELECT` runs outside the transaction as a snapshot read. If two writers with the same `client_message_id` both miss it, both open a transaction and the `INSERT … ON CONFLICT DO NOTHING RETURNING 1` lets exactly one claim the key; the loser gets **zero rows, must `ROLLBACK` without allocating, and must re-run the fast-path `SELECT`** to return the winner's `(seq, message_id)`. That re-read on a zero-row claim is mandatory application logic, not an optional retry — it is what makes the pattern correct under the TOCTOU window between the outside-transaction read and the in-transaction claim. The whole scheme is safe at Postgres's default **read-committed** isolation and does **not** require `serializable`: the winner's row is committed before the loser re-reads it, and the counter is only ever advanced inside a successful claim.

This is ADR-004 **Option 5 (Database-Generated Sequences)**, which the original ADR rejected *only* because of the single-store constraint now lifted. It is strictly simpler than the chosen two-phase DynamoDB design *for the happy path*: allocation and persistence are one atomic unit, so a failed write rolls the counter back (fewer gaps than DynamoDB, though gaps remain permitted per ADR-001). Idempotency remains a check-before-allocate step, exactly as DynamoDB required — the transaction does not remove that ordering constraint, it re-expresses it. The per-chat counter row is a row-level lock — the same hot key the DynamoDB atomic counter was, now legible as a Postgres lock, and not a *new* bottleneck because per-chat writes are already serialised by the ordering requirement itself.

The cost of the split, named honestly: **two provisioning targets**, and **cross-store referential integrity is application-enforced** — a `messages.chat_id` in Postgres points at a `chats` document in Firestore with no database-level foreign key. This is not a regression (DynamoDB single-table design already enforced entity relationships in application code), but it is a property the write-path and read-path code must respect.

### Axis B — Compute (replaces ECS Fargate)

| Option | Verdict | Reasoning |
|---|---|---|
| **GKE Autopilot** | **Chosen** | Pods hold WebSocket connections for their full lifetime — no request-timeout cap. One deployment model for all four services. $0.10/hr cluster fee + pay-per-pod-request; negligible in a deploy-destroy window. The author is explicitly open to Kubernetes, and a single Autopilot cluster is the cleanest "all services, one substrate" story. |
| Cloud Run | Rejected | Simplest option, but caps a WebSocket connection at **60 minutes**, forcing an hourly reconnect. ADR-009 makes the system reconnect-tolerant, so this is survivable — but it is a substrate constraint leaking into a client-visible behaviour, and splitting the stateful Gateway onto GKE while stateless services run on Cloud Run would mean maintaining two deployment models. |
| Compute Engine (raw VMs) | Rejected | Manual capacity, patching, and scaling — undifferentiated work ADR-014 already rejected in its EC2 analysis. |

**Decision B: GKE Autopilot** runs all four services (Gateway, Ingest, Fanout, Chat Management) as Deployments in one cluster.

Two consequences of this choice are **binding deployment requirements**, not runtime tunables, and must ship in the initial Terraform module (see *Deployment requirements* below):

- **Load-balancer WebSocket timeout.** GCP's external Application Load Balancer applies **two independent limits** to a WebSocket, and they must not be conflated. (a) The **backend-service `timeoutSec`** is an *idle* timeout — default **30 seconds** — after which a *silent* connection is dropped; it does not apply to a connection carrying traffic. ADR-005's heartbeat keeps the connection non-idle, but relying on that alone is fragile, so `timeoutSec` must still be raised to a large value (via `GCPBackendPolicy` under the Gateway API, or `BackendConfig` under Ingress) with the heartbeat interval kept comfortably below it. (b) Separately and **non-customizably, every active WebSocket is force-closed at a fixed 24-hour ceiling**, regardless of traffic — this is a documented hard limit on the external ALB, not a function of `timeoutSec`. The 24 h ceiling is the like-for-like comparison against Cloud Run's hard **60-minute** active cap, and it is why GKE wins for a long-lived-connection workload: the forced reconnect the client must tolerate is daily, not hourly. Both limits are survivable because ADR-009 makes reconnection a first-class path; neither may be left at its default unexamined.
- **Cloud SQL connection ceiling.** A `db-f1-micro` allows ~25 connections; GKE Autopilot scales pods horizontally, so `replicas × pool_size` can exhaust the database. The initial deployment must front Cloud SQL with a pooler (**PgBouncer** in transaction-pooling mode, as a Deployment or the Cloud SQL Auth Proxy sidecar with pooling) *or* bound the Ingest/Chat-Management replica counts explicitly. Silence here is the most common Postgres-on-Kubernetes failure mode; the ADR chooses PgBouncer.

### Axis C — Event log (Kafka provider)

**Decision C: Google Cloud Managed Service for Apache Kafka.** It exposes the real Kafka API, so ADR-011's explicit-partitioning contract (`partition = murmur2(chat_id) % N`) and the `franz-go` client survive with only an authentication change (MSK-IAM → SASL/OAUTHBEARER or mTLS). Minimum cluster is 3 vCPU / 3 GiB at ~$0.27/hr compute; a deploy-destroy session costs a few dollars, so the earlier "$197/month Managed Kafka" concern does not apply to short-lived dev use. **Redpanda is dropped entirely** — it existed only to run Kafka locally, and local infrastructure is withdrawn. Pub/Sub was rejected because its lack of a partition-ordered log would force a rewrite of ADR-011 and the per-chat ordering story.

### Axis D — Ephemeral cache / presence (Redis provider)

**Decision D: Memorystore for Redis.** The Redis API is identical, so ADR-010's data structures, TTLs, and ownership rules are unchanged; only the provider name moves. Per ADR-003 Redis is ephemeral-by-contract, so no durability guarantee is affected.

### Axis E — Observability backend

**Decision E: Google Cloud Managed Service for Prometheus + Cloud Trace + Cloud Logging.** ADR-012 deliberately specified backend-agnostic OpenTelemetry contracts; this is an exporter-configuration change with no application-code impact. (Grafana Cloud, already used in the sibling ateliers, remains a drop-in alternative.)

### Axis F — Local development

**Decision F: Local cloud-emulation removed; the Docker toolchain retained.** Two things were bundled under "local dev" and must be separated:

- **Removed — local cloud-service emulation.** No LocalStack (DynamoDB/MSK/etc. emulators) and no local infrastructure services standing in for cloud dependencies. Integration and end-to-end testing run against a Terraform-provisioned GCP dev project, deployed and destroyed per session.
- **Retained — Docker / Docker Compose as the reproducible development *workspace*.** Nothing is installed on the host. The toolchain — `gcloud`, `terraform`, `kubectl`, `buf`, the Go toolchain, `golangci-lint`, test runners — runs inside containers, so the project is buildable and operable on any machine with only Docker present. This is a hard, non-negotiable constraint: reproducibility of the *toolchain* is independent of where the *infrastructure* lives. The workspace container simply targets a real GCP project instead of a local emulator.

Unit tests remain hermetic and run inside the workspace container with no cloud dependency (they always did).

### Axis G — Analytical data lake (new scope)

**Decision G: A BigQuery Sink connector on the Managed Kafka cluster** streams the event topics (`messages.persisted`, `memberships.changed`, `chats.created`) into BigQuery raw landing tables, optionally staging through GCS for a BigLake external-table pattern. Detailed schema, partitioning, and retention design is deferred to **ADR-022 (Analytics Data Lake)**; ADR-021 establishes the tap in scope and records its dataflow impact (see below). This activates a consumer that ADR-003 already anticipated ("consumers may rebuild derived state"; "Analytics (future)").

## Impact on Prior ADRs

The migration's most important finding is how *little* it touches. Of twenty prior ADRs, thirteen are untouched invariants — they are about ordering, delivery, protocol, and Go internals, not about any cloud. Seven are substrate-coupled.

| Tier | ADRs | Disposition |
|---|---|---|
| **Superseded** (decision outcome changed) | **004** (sequencing → Postgres Option 5, one transaction), **007** (data model → **polyglot**: Postgres write-path tables + Firestore document collections), **014** (tech stack → this ADR) | Body retained; superseded banner added; ADR-021 (and, for the two-store schema, a follow-up amendment to ADR-007) carries the new decision. |
| **Amended** (mechanism/provider changed, contract intact) | **003** (Postgres replaces DynamoDB as authoritative; BigQuery added as analytical history), **010** (ElastiCache → Memorystore), **011** (MSK → Managed Kafka; client auth; + BigQuery sink consumer), **012** (CloudWatch/X-Ray → Managed Prometheus/Trace) | Amended banner added pointing here; original text stands. |
| **Untouched invariants** (contract survives the migration unchanged) | **001** (ordering/delivery/idempotency contract), **002** (plane separation), **005** (WebSocket protocol), **006** (REST contract), **008** (delivery watermark semantics), **009** (backpressure/reconnection), **013** (security/abuse), **015** (auth/OTP), **016** (chat lifecycle), **017** (client contract), **018/019/020** (Go service internals) | Contract unchanged. Three of these have their **backing store re-homed** without any contract change: 008 `delivery_state` and the message tables → Postgres; 015 `sessions` and 016 `memberships` → Firestore. The storage move is covered by ADR-007's rewrite; the behavioural contract is identical. |

**13 of 20 _contracts_ survive a full cloud migration untouched.** The claim is deliberately scoped to contracts, not implementations: three of the thirteen (008, 015, 016) keep their contract while their backing store is re-homed between Postgres and Firestore. That the *behavioural* corpus is 65% substrate-independent is the argument for treating these ADRs as a durable asset rather than AWS-specific documentation.

## The Data Lake — why it affects the design now

Deferring the analytical tier "to later" would be a mistake, because three of its consequences reach back into decisions being made in this ADR:

1. **Event schemas become a published contract.** Once BigQuery consumes the topics, the event envelope is no longer a private fanout detail — it is an analytical schema other queries depend on. This strengthens the case (already latent in ADR-011's poison-pill handling) for stable, versioned event schemas (Avro/Protobuf with a registry) rather than ad-hoc JSON.
2. **The "complete history" invariant moves — and must be scoped honestly.** ADR-003 asserts that Kafka is a 7-day operational log and DynamoDB is "the only complete historical source." That single-complete-source guarantee does **not** survive the migration intact, and it would be dishonest to claim it does. History is now spread across three *partial* stores: Postgres (current message write-path + delivery state, operational not historical), BigQuery (only the events Kafka actually emits — message-persistence and membership/chat-creation — and only since the sink was activated), and Firestore (current entity state, with **no changelog** — a chat deletion, a membership revocation, or a profile edit emits no event and leaves no history). The precise, defensible claim is therefore narrow: *"BigQuery is the complete history of the events emitted to Kafka, from sink activation onward."* Questions like "what was chat X's membership three months ago?" are **not** answerable today. Closing that gap (Firestore change-data-capture into Kafka/BigQuery, or emitting mutation/deletion events) is required work, and **ADR-022 must enumerate the coverage gaps before this amendment is accepted.**
3. **Privacy surface expands.** Streaming message bodies into an analytical store raises retention and PII questions that ADR-013 scoped narrowly. ADR-022 must decide what is streamed (full bodies vs. metadata-only), and this is a design-time decision because it constrains the sink connector's field selection.

These three points are the reason the author's instinct — "this affects the initial design, keep it in mind now" — is correct. ADR-022 will do the detailed design; ADR-021 records that the event log now has two jobs.

## Deployment Requirements and Operational Guards

These are binding conditions on the first Terraform apply, not optional tuning. Each is a direct consequence of a decision above.

1. **LB WebSocket timeout** (from Decision B). The Gateway's external-LB backend must set a large `timeoutSec` via `GCPBackendPolicy` (Gateway API) or `BackendConfig` (Ingress); the default 30 s idle timeout is disqualifying. ADR-005's heartbeat interval must stay below it.
2. **Cloud SQL connection pooling** (from Decision A / Open Q1). PgBouncer (transaction pooling) fronts Cloud SQL, or Ingest/Chat-Management replicas are explicitly bounded. Required before any horizontal scaling. **Driver caveat:** transaction pooling returns the connection to the pool between statements, which breaks connection-scoped server-side prepared statements — and Go's `pgx` (the ADR-014 driver) uses them by default. The service must therefore either disable prepared-statement caching in `pgx` (`default_query_exec_mode = QueryExecModeSimpleProtocol`, or set the statement-cache to zero) or run PgBouncer 1.21+ with `max_prepared_statements > 0` (its transaction-mode prepared-statement support). This is a config decision to make at implementation time, not an architectural one, but it must not be discovered at runtime.
3. **Event-schema format is decided _before_ the Kafka cluster is provisioned** (blocking dependency on ADR-022 / Open Q2). Once BigQuery consumes the topics the envelope is a published contract, and ADR-011 currently specifies JSON. If the cluster is provisioned and topics begin producing JSON, moving to Avro/Protobuf + a schema registry becomes a breaking topic migration rather than a greenfield choice. Therefore **ADR-022 (or an amendment to ADR-011) must fix the wire format before the Managed Kafka cluster is created.** This ordering is a hard dependency, not a preference.
4. **Budget guard** (from the deploy-and-destroy model / Open Q3). A forgotten session — GKE ~$0.10/hr + Managed Kafka ~$0.27/hr + Cloud SQL + Memorystore — is roughly $250–300/month against a ~$1,700/month trial. Deploy-and-destroy (Decision Driver 5) is only viable with a guard: a GCP **budget alert** (e.g. at $500 cumulative), and `terraform destroy` as the mandatory end-of-session step. Without this, the credit can be silently drained by an instance nobody is using.

## Acceptance Conditions

This ADR is **Accepted**. Its infrastructure must **not** be applied in any environment until these conditions hold:

1. **ADR-022 reaches at least Proposed status and fixes the Kafka event-schema wire format** *before* the Managed Kafka cluster is provisioned in any environment (see Data Lake §2 and Deployment Requirements §3). Provisioning the cluster with JSON topics first turns the Avro/Protobuf move into a breaking migration; the wire format is therefore a greenfield decision that must precede the cluster, not follow it.
2. **ADR-022 enumerates the history-coverage gaps** the narrowed complete-history invariant leaves open (Firestore mutations/deletions, pre-sink events), so the amendment to ADR-003 is accepted with its limits documented rather than implied.
3. **The follow-up amendment to ADR-007** specifies the two-store schema (Postgres write/delivery tables + Firestore collections) and the application-enforced cross-store integrity rules.

Conditions 1–2 are hard sequencing gates on infrastructure; condition 3 may proceed in parallel with early implementation but must land before the data model is treated as authoritative.

## Consequences

### Positive

- **ADR-004 gets simpler.** Two phases collapse into one transaction; the gap window shrinks; the mechanism is legible to anyone who reads SQL.
- **The contract corpus is validated.** The migration demonstrates empirically that 13/20 decisions were substrate-independent — the strongest possible evidence that the architecture was designed at the right altitude.
- **The data lake is native and cheap.** A managed connector, not a bespoke pipeline, feeds BigQuery.
- **Operational surface shrinks where it should.** No LocalStack parity to maintain; one compute model; managed data/event/cache tiers. The reproducible Docker toolchain is kept, so "runnable on any machine with only Docker" survives the migration.
- **Polyglot persistence is a deliberate, justified departure.** Each store is chosen for its access pattern — transactional write path in Postgres, read-mostly documents in Firestore — the exact "justify every departure from the relational model" exercise the lab exists to practise.

### Negative

- **A running Postgres primary is not scale-to-zero.** Unlike DynamoDB, Cloud SQL bills while it exists. Mitigated by deploy-and-destroy discipline plus the budget alert and mandatory end-of-session `terraform destroy` (see Deployment Requirements §4); a forgotten instance is the main budget risk, and it is a guarded one, not an accepted one.
- **The per-chat counter is now a visible row lock.** Write throughput per chat is bounded by lock contention on one row — the same ceiling DynamoDB had, now explicit. This is the throughput prediction to test (see ADR-004's residual risk and the series' Artifact 00).
- **ADR-007 requires a genuine rewrite,** not a rename: single-table DynamoDB design → a **two-store model** (normalised relational tables for the write path; Firestore document collections for entity state), with the store boundary and cross-store integrity rules made explicit. This is real work, tracked as a follow-up amendment.
- **Cross-store referential integrity is application-enforced.** A `messages.chat_id` (Postgres) references a `chats` document (Firestore) with no database-level foreign key. Not a regression from DynamoDB single-table, but a rule the code must uphold.
- **Kafka client auth changes.** `franz-go`'s MSK-IAM path is replaced by SASL/OAUTHBEARER or mTLS against Managed Kafka — a small but non-zero code change in the producer/consumer setup.

### Neutral

- The three-plane architecture (ADR-002) maps onto GKE Deployments exactly as it mapped onto ECS services.
- Redis and observability changes are provider renames behind stable APIs.
