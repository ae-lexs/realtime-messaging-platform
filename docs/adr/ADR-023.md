# ADR-023: Data Model — Two-Store Schema (Postgres Write/Delivery Path + Firestore Identity/Membership)

- **Status**: Accepted
- **Date**: 2026-07-24
- **Supersedes**: [ADR-007](ADR-007.md) (the single-table DynamoDB data model — this ADR is the concrete two-store schema its banner promised)
- **Realizes**: [ADR-021](ADR-021.md) D-A (the polyglot datastore split)
- **Incorporates**: [ADR-022](ADR-022.md) (the `outbox` table)

---

## Context and Problem Statement

ADR-021 replaced DynamoDB with a **polyglot split** — Cloud SQL for PostgreSQL owns the ordered message/delivery write path; Firestore (native mode) owns identity and membership — and drew the boundary at the atomic write path. ADR-007 specified the data model as **8 DynamoDB tables** under a single-table-family design with three GSIs. Its own superseded-banner promises "a follow-up amendment [that] will specify the concrete schema." ADR-022 then added one more table (`outbox`) to make message-event production transactional.

This ADR is that concrete schema. It is a **faithful translation**, not a redesign: every table, key, and access pattern in ADR-007 is preserved, re-expressed in the target store, with the substrate-level differences (TTL, consistency defaults, secondary indexes, monotonic updates) surfaced honestly rather than glossed. It is the artifact the first implementation PR builds against.

**Core question:** What are the exact Postgres tables and Firestore collections, their keys and indexes, the SQL/queries for each ADR-007 access pattern, and the cross-store integrity rules — such that nothing ADR-007 guaranteed is lost and the ADR-021/022 decisions are concretely realized?

---

## Decision Drivers

1. **Access-pattern parity.** Every access pattern in ADR-007 §4 must map to a concrete query with equal-or-better efficiency and consistency. Losing one is a defect.
2. **The write-path boundary is load-bearing.** `chat_counters`, `messages`, `idempotency_keys`, `delivery_state`, and `outbox` share one Postgres transaction where ADR-004/ADR-021/ADR-022 require atomicity; they cannot straddle stores.
3. **Honest substrate differences.** DynamoDB gave native item TTL and default eventual consistency; Postgres and Firestore differ on both. Where a guarantee changes, it is named, not hidden.
4. **No manual index sprawl.** Prefer the store's automatic indexing (Postgres PKs, Firestore single-field indexes) over hand-declared ones, matching ADR-007's GSI-minimization ethos.
5. **Cross-store integrity is application-enforced.** No database-level foreign key spans Postgres and Firestore; the rules must be enumerated so code upholds them.

---

## The store boundary

| Store | Tables / collections | Why here |
|---|---|---|
| **Cloud SQL for PostgreSQL** (message & delivery path) | `chat_counters`, `messages`, `idempotency_keys`, `delivery_state`, `outbox` | On, or transactional with, the ordered write path (ADR-004/021/022). `delivery_state` is compared against `messages.sequence` in reconnect-sync, so it shares the store and failure domain (ADR-021 Issue-4 resolution). |
| **Firestore, native mode** (identity & membership) | `users`, `chats`, `memberships`, `sessions`, `otp_requests`, `phone_index` | Read-mostly documents with no cross-entity transaction requirement; serverless, scales to zero. |

ADR-007's 8 tables map 1:1 (`chat_memberships` → `memberships`), plus the new `outbox`. Auth-transient state (`otp_requests`, ADR-015) follows the identity tier into Firestore and inherits its native TTL; v1.2 specifies it below, together with the `phone_index` uniqueness sentinel ADR-015 §5.1 requires. Both are outside ADR-007's data-model scope — they are the auth tables ADR-015 introduced — but they live in this store, so they are specified here rather than left to the implementation.

## Postgres schema (write & delivery path)

```sql
-- 1. chat_counters — one row per chat; the sequence source (ADR-004 Option 5, ADR-021 D-A).
CREATE TABLE chat_counters (
  chat_id     TEXT PRIMARY KEY,
  seq         BIGINT      NOT NULL DEFAULT 0,   -- was DynamoDB `sequence_counter`
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 2. messages — composite PK (chat_id, sequence) replaces DynamoDB PK+SK.
CREATE TABLE messages (
  chat_id            TEXT   NOT NULL,
  sequence           BIGINT NOT NULL,             -- ALLOCATED from chat_counters, not a serial
  message_id         TEXT   NOT NULL,             -- ULID, globally unique
  sender_id          TEXT   NOT NULL,             -- -> Firestore users/{id} (app-enforced)
  client_message_id  TEXT   NOT NULL,
  content            TEXT   NOT NULL CHECK (octet_length(content) <= 4096),  -- 4096 BYTES (storage), matching ADR-007's "4KB"; use char_length() if a semantic character limit is meant
  content_type       TEXT   NOT NULL DEFAULT 'text/plain',
  created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (chat_id, sequence)
);
CREATE UNIQUE INDEX messages_message_id_uk ON messages (message_id);
-- "after sequence" and "recent N" are both served by the PK's (chat_id, sequence) ordering; no GSI (ADR-007).

-- 3. idempotency_keys — composite PK; check-before-allocate per ADR-021.
CREATE TABLE idempotency_keys (
  chat_id            TEXT   NOT NULL,
  client_message_id  TEXT   NOT NULL,
  message_id         TEXT,                        -- filled after the write claims the key
  sequence           BIGINT,
  created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at         TIMESTAMPTZ NOT NULL,        -- created_at + 7 days; see TTL note below
  PRIMARY KEY (chat_id, client_message_id)
);
CREATE INDEX idempotency_keys_expires_idx ON idempotency_keys (expires_at);

-- 4. delivery_state — composite PK (user_id, chat_id); user-centric, monotonic watermark.
CREATE TABLE delivery_state (
  user_id              TEXT   NOT NULL,           -- -> Firestore users/{id} (app-enforced)
  chat_id              TEXT   NOT NULL,
  last_acked_sequence  BIGINT NOT NULL,
  updated_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, chat_id)
);

-- 5. outbox — new (ADR-022); written in the SAME txn as messages; drained by the in-process relay.
CREATE TABLE outbox (
  id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  chat_id       TEXT   NOT NULL,
  sequence      BIGINT NOT NULL,
  event_id      TEXT   NOT NULL,                  -- ULID; the sink's UPSERT/dedup key (ADR-022 D2)
  event_type    TEXT   NOT NULL,                  -- 'MessagePersisted'
  payload       BYTEA  NOT NULL,                  -- serialized events.v1 Protobuf (ADR-022 D1)
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  claimed_at    TIMESTAMPTZ,                      -- set when a relay worker takes the row (NOT durability)
  published_at  TIMESTAMPTZ                       -- set ONLY after Kafka acks=all (see relay statement)
);
-- Partial index powers the relay's claim query (ADR-022 D4); covers rows not yet Kafka-confirmed
-- (published_at IS NULL, including in-flight claimed rows):
CREATE INDEX outbox_unpublished_idx ON outbox (chat_id, sequence) WHERE published_at IS NULL;
```

**The load-bearing statements** (the SQL other ADRs specify, gathered here). **Invariant: every read below targets the Cloud SQL primary.** Cloud SQL HA is a primary + a *standby* (failover), not a read replica; this schema routes **no** reads to a follower. That invariant is what makes the idempotency re-read (step 1) safe: after a lost claim, the winner's row is committed, so a fresh read-committed `SELECT` on the primary is guaranteed to see it — there is no replica-lag window.

```sql
-- (0) Idempotency FAST PATH (the retry case): return the ORIGINAL result; no allocation, no write.
--     Runs on the primary (see invariant above).
SELECT sequence, message_id FROM idempotency_keys
  WHERE chat_id = $1 AND client_message_id = $2;
-- If a row is found, return (sequence, message_id) and stop.

-- (1) FIRST SIGHT: one transaction. Claim the key first; a committed conflict returns 0 rows, so
--     ROLLBACK and re-run step (0) on the primary — the winner is committed and therefore visible.
BEGIN;   -- steps (1a)+(1b) are ONE transaction; the claim INSERT and the CTE must NOT be split
-- (1a) claim:
INSERT INTO idempotency_keys (chat_id, client_message_id) VALUES ($1,$2)
  ON CONFLICT DO NOTHING RETURNING 1;               -- 0 rows => ROLLBACK, re-run (0) on the primary
-- (1b) same transaction — allocate + write message + outbox, then backfill the key:
WITH alloc AS (
  UPDATE chat_counters SET seq = seq + 1, updated_at = now() WHERE chat_id = $1 RETURNING seq
), ins AS (
  INSERT INTO messages (chat_id, sequence, message_id, sender_id, client_message_id, content, content_type)
    SELECT $1, alloc.seq, $3, $4, $2, $5, $6 FROM alloc RETURNING sequence, message_id
), obx AS (
  INSERT INTO outbox (chat_id, sequence, event_id, event_type, payload)
    SELECT $1, ins.sequence, $7, 'MessagePersisted', $8 FROM ins
)
UPDATE idempotency_keys SET message_id = ins.message_id, sequence = ins.sequence
  FROM ins WHERE chat_id = $1 AND client_message_id = $2;
COMMIT;  -- (1a) and (1b) commit together, or not at all

-- (2) Monotonic delivery watermark (ADR-008; replaces the DynamoDB conditional UpdateItem):
INSERT INTO delivery_state (user_id, chat_id, last_acked_sequence) VALUES ($1,$2,$3)
  ON CONFLICT (user_id, chat_id) DO UPDATE
    SET last_acked_sequence = EXCLUDED.last_acked_sequence, updated_at = now()
    WHERE delivery_state.last_acked_sequence < EXCLUDED.last_acked_sequence;  -- never moves backward

-- (3) Relay: CLAIM -> produce(acks=all) -> mark PUBLISHED. published_at is set ONLY after the broker
--     durably acks, never before it — the transactional-outbox invariant. A crash between claim and ack
--     leaves published_at NULL; the row is reclaimed (at-least-once) and the duplicate is deduped
--     downstream by the sink's event_id UPSERT (ADR-022 D2). Setting published_at at claim time would
--     silently lose the event on such a crash.
--   3a. CLAIM (atomic; skips rows another worker holds; reclaims rows claimed-but-not-published > 30s):
UPDATE outbox SET claimed_at = now()
  WHERE id IN (SELECT id FROM outbox
               WHERE published_at IS NULL AND (claimed_at IS NULL OR claimed_at < now() - interval '30 seconds')
               ORDER BY chat_id, sequence FOR UPDATE SKIP LOCKED LIMIT :n)
  RETURNING id, chat_id, sequence, event_id, event_type, payload;
--   3b. For each row: produce to Kafka with acks=all (partition key = chat_id, preserving per-chat order),
--       and ONLY on the broker's ack:
UPDATE outbox SET published_at = now() WHERE id = $id;
```

**Relay constants.** The 30-second reclaim window is ~6× the 5 s Kafka produce timeout (ADR-009), not a magic number — long enough that a healthy `acks=all` publish always completes before its row becomes reclaimable, short enough to bound the loss-visibility window. One consequence to expect and *not* alert on as anomalous: a simultaneous restart of all relay replicas makes every row claimed in the last 30 s eligible for re-claim at once, so a rolling restart yields a brief burst of duplicate publishes — harmless, absorbed by the sink's `event_id` upsert (ADR-022 D2).

## Firestore model (identity & membership)

Native mode; document reads **and queries are strongly consistent** (stronger than DynamoDB's eventual-by-default). Firestore auto-indexes every single field, so the DynamoDB GSIs become plain equality queries with no manual index config.

| Collection | Doc ID | Fields | Replaces |
|---|---|---|---|
| `users/{user_id}` | UUID | `phone_number` (E.164), `phone_verified`, `display_name`, `created_at`, `updated_at` | `users` table |
| `chats/{chat_id}` | UUID | `chat_type` (`direct`\|`group`), `name`, `created_by`, `created_at`, `updated_at` | `chats` table |
| `memberships/{chat_id}__{user_id}` | deterministic composite | `chat_id`, `user_id`, `role` (`owner`\|`admin`\|`member`), `joined_at`, `muted_until` | `chat_memberships` + `user_chats-index` |
| `sessions/{session_id}` | UUID | `user_id`, `device_id`, `refresh_token_hash` (SHA-256), `created_at`, `expires_at` | `sessions` + `user_sessions-index` |
| `otp_requests/{phone_hash}` | SHA-256 of the E.164 number | `otp_mac`, `status` (`pending`\|`verified`), `attempt_count`, `created_at`, `expires_at` | `otp_requests` (ADR-015 §1.1) |
| `phone_index/{phone_hash}` | SHA-256 of the E.164 number | `user_id`, `created_at` | the `PHONE#` sentinel item (ADR-015 §5.1) |
| `direct_chats/{min(user_a,user_b)}__{max(user_a,user_b)}` | deterministic composite, the pair sorted lexicographically | `chat_id`, `created_at` | the `direct_chat_index` table (ADR-016 §2.1) |

*(Doc-ID types read "ULID" until v1.3; the implemented identifiers are UUIDs and have been since M1.1 — v1.1's changelog recorded the correction without updating this table.)*

- **`users` phone lookup** (was `phone_number-index` GSI): `users.where('phone_number','==',x).limit(1)` — auto-indexed.
- **`memberships` bidirectional queries** (was base table + `user_chats-index`): the **deterministic doc ID `{chat_id}__{user_id}`** makes "check membership" a direct `get()` (strongly consistent); "list chat members" is `where('chat_id','==',c)` and "list user's chats" is `where('user_id','==',u)` — both on auto single-field indexes. No manual GSI, both directions served. **Doc-ID invariant:** two UUIDs + separator = **74 bytes** (36 + 2 + 36), well under Firestore's 1,500-byte document-ID limit; changing the ID format (longer IDs, namespaces) requires re-validating this bound. It binds `direct_chats` too, which is built the same way from two user IDs. **History caveat:** because the doc ID is deterministic, `delete` then re-`set` overwrites `joined_at` — the collection holds *current* membership, not history. That is acceptable (ADR-008/016 need current state only); if "was this user ever a member?" is ever required, the answer is **`lake.raw_memberships_changed`** — the `memberships.changed` events *are* streamed to BigQuery in v1 (ADR-022 D2), so change history exists there, just not in this current-state collection. (This is distinct from ADR-022's G2 gap, which is about entity mutations that emit *no* event — e.g. chat deletion or profile edits.)
- **`sessions` per-user list** (was `user_sessions-index`): `sessions.where('user_id','==',u)`.
- **`sessions` TTL**: a **Firestore TTL policy on `expires_at`** replaces the DynamoDB `ttl` attribute — native, no sweeper. **But TTL deletion is not instantaneous** — Firestore removes expired documents within ~24 h of `expires_at`, so an expired session can still be *readable* for up to a day. The auth service therefore **must validate `expires_at` in application code** on every `get(sessions/{id})` and reject an expired session; TTL is garbage collection, never the correctness gate.
- **`otp_requests` TTL and the create-if-absent-or-expired rule** (v1.2). A second TTL policy covers `otp_requests.expires_at`, so this store needs no sweeper either. The ≤24 h TTL lag bites much harder here than it does on sessions, because an OTP is valid for **5 minutes**: for the remaining ~23.9 hours the document is expired but still present. Two consequences, both mandatory: verification **must** gate on `expires_at` in code (as sessions do), and `RequestOTP` **cannot** use a bare `Create()` to implement ADR-015 §1.2's `attribute_not_exists(phone_hash)` conditional put — that would return `AlreadyExists` for an OTP that lapsed minutes ago and lock the phone number out for a day. The conditional put translates to a **transaction**: read the document, and write only if it is absent *or* past `expires_at`; otherwise return the existing record's expiry. The raw phone number is never stored (ADR-015 §1.1), so the document ID is the SHA-256 hash and nothing here is queried by phone.
- **`phone_index` is the uniqueness sentinel, and Firestore genuinely needs it.** ADR-015 §5.1 enforces one user per phone number with a `PHONE#{phone_hash}` item written under `attribute_not_exists` inside the registration transaction, because the `phone_number-index` GSI was eventually consistent and two concurrent registrations could both read "no user". **Firestore's strong consistency does not retire that argument.** A Firestore transaction locks the documents it *reads*; a query that matches nothing locks nothing, so there is **no phantom protection** — two concurrent first-time registrations of the same number would both observe an empty `where('phone_number','==',x)` result and both commit, silently producing two users. `tx.Create(phone_index/{phone_hash})` fails atomically if the document exists, which is the exact guarantee `attribute_not_exists` gave. The division of labour is unchanged from DynamoDB: `users.phone_number` and its equality query serve **reads**; `phone_index` serves **uniqueness** only. It carries no TTL — it is permanent, like the user it guards.
- **`direct_chats` is the second uniqueness sentinel, and it exists for the same reason as the first** (v1.3). ADR-016 §2.1 enforces "at most one direct chat per user pair" with a `direct_chat_index` item keyed `{min}#{max}` under `attribute_not_exists`; ADR-006 §4.1 supplies the canonicalisation that makes the key well-defined — *"member_ids are sorted lexicographically to ensure `{A, B}` and `{B, A}` map to the same chat"*. Both survive the substrate change intact. What changes is only where the sentinel lives, and the argument for keeping it is **exactly `phone_index`'s**: "is there a direct chat containing A and B?" has no answer a Firestore transaction can lock. `memberships.where('user_id','==',A)` returns nothing before the chat exists, and a query matching nothing locks nothing, so two concurrent `POST /chats {type: direct}` for one pair both observe "no chat" and both commit. The result is not a duplicate row that a reconciler can merge later: it is **two chat IDs for one conversation**, each with its own `chat_counters` sequence in Postgres and its own message history, with the two clients writing into different chats while both believe they are talking to each other.
  - **Doc ID:** the two user IDs sorted lexicographically as strings and joined by `__` — `min(a,b) + "__" + max(a,b)` — so both argument orders address one document. The separator is `__`, matching `memberships`, **not** ADR-016 §2.1's `#`. That ADR chose `#` because "user IDs are ULIDs which use `[0-9A-Z]`", and the implemented IDs are UUIDs (v1.1), whose alphabet is `[0-9a-f-]`: neither `#` nor `_` can occur in one, so both separators are unambiguous and consistency with the collection next door decides it.
  - **Value:** `chat_id` — the sentinel is what the loser of a race reads to learn which chat won. That makes it the one sentinel here that is *also* a lookup, unlike `phone_index`.
  - **Why not make the chat ID itself deterministic** (`chats/{hash(pair)}`, no second collection)? Because a chat ID is not private. It appears in REST paths (ADR-006), as the Kafka partition key (ADR-011), in `lake.raw_*` rows (ADR-022) and in client caches — and a chat ID derived from its members turns every one of those into a disclosure of who is in the conversation, permanently, since the ID cannot be rotated without breaking the message history keyed by it. This is the same split as `users.phone_number` versus `phone_index`: the identifier that travels stays opaque, and the contended one is a separate document whose only job is to be contended for.
  - **Scope: direct chats only.** Two groups with identical membership are legitimately different chats (ADR-006 §4.2), so nothing is written here for `chat_type = "group"` — the collection is empty of them by construction, not by filter.
  - **No TTL.** Permanent, like `phone_index`. If direct-chat deletion is ever implemented, the sentinel must be deleted in the same transaction as the chat (ADR-016 §2.1's standing note), or the pair can never open a second conversation.
  - **The creation transaction** (ADR-016 §2.2, re-homed): read `direct_chats/{pair}` first — Firestore requires every read in a transaction to precede every write — then `tx.Create` the sentinel, the `chats/{chat_id}` document and **two** `memberships/{chat_id}__{user_id}` documents. Four documents, all-or-nothing. The read is the fast path that returns an existing chat without contending; the `Create` is what actually enforces uniqueness, since the read of an absent document is what locks nothing.
  - **ADR-016's fifth item does not come with it, and that is a gap M1.3 must close.** Its transaction wrote `chat_counters {seq: 0}` alongside the other four, which is no longer possible: the counter is a **Postgres** row (ADR-021 D-A) and cannot join a Firestore transaction. Chat creation therefore straddles the stores, and the failure to expect is a chat that exists with no counter, whose first message fails on an `UPDATE chat_counters … RETURNING seq` that matches no row. The resolution belongs to M2.2 with the allocation statement rather than here, but the shape is already visible: make the counter **self-creating on first use** (upsert-then-return, so no chat-creation write is needed at all) rather than inserting it after the Firestore commit and owning a second failure window. Recorded now because the load-bearing SQL above assumes the row exists, and nothing else says who puts it there.
  - **The loser of this race can complete, and the loser of the registration race cannot.** Worth stating together, because the two look identical and are not. A losing `verify-otp` holds an OTP the winner already consumed, so it has nothing left to spend (ADR-015 §10.2, corrected in v1.4). A losing direct-chat create has consumed nothing: it re-reads `direct_chats/{pair}`, finds the winner's `chat_id`, and returns it as `200 OK` — which is precisely what the caller asked for and exactly ADR-006 §4.1's idempotent-create contract. A race that the caller never learns about is the correct outcome here.

## Cross-store integrity (application-enforced)

No foreign key spans the two stores; these references are upheld in code (as they were in DynamoDB's single-table world — not a regression):

| Reference | From (Postgres) | To (Firestore) |
|---|---|---|
| message author | `messages.sender_id` | `users/{id}` |
| message chat, counter chat, watermark chat | `messages.chat_id`, `chat_counters.chat_id`, `delivery_state.chat_id` | `chats/{id}` |
| watermark user | `delivery_state.user_id` | `users/{id}` |

Within Firestore, `memberships.chat_id → chats/{id}` and `memberships.user_id → users/{id}` are likewise app-enforced (Firestore has no FKs).

**Application-enforced invariant (not a cross-store reference, but audited here so it is not lost in an auth refactor):** the auth service **must** check `sessions.expires_at` in code on every `get(sessions/{id})` and reject an expired session. Firestore TTL (≤24 h lag) is garbage collection, never the correctness gate (see Firestore model).

## Substrate-difference deltas (the honest translation)

| Concern | DynamoDB (ADR-007) | This schema | Impact |
|---|---|---|---|
| **Idempotency TTL** | Native item TTL (7 d) | Postgres has **no native row TTL** — `expires_at` column + a scheduled sweep (`pg_cron`: `DELETE FROM idempotency_keys WHERE expires_at < now()`) | New operational job; the only place the migration adds a sweeper |
| **Session TTL** | Native item TTL | **Firestore native TTL policy** on `expires_at` | Clean; no sweeper |
| **Read consistency** | Eventual by default; strong via `ConsistentRead` | Postgres reads strong (read-committed); Firestore reads/queries strong | ADR-007's "Strongly" patterns (list members, check membership) are met or **exceeded** |
| **Monotonic watermark** | Conditional `UpdateItem` | `INSERT … ON CONFLICT DO UPDATE … WHERE last < new` | Equivalent guarantee |
| **Secondary access** | 3 GSIs (phone, user-chats, user-sessions) | Firestore automatic single-field indexes | No manual index config; less write amplification to reason about |
| **Sequence source** | DynamoDB atomic counter | `chat_counters` row + `UPDATE … RETURNING` | Two phases → one txn (ADR-004/021) |

---

**Sweep discipline (`idempotency_keys` and `outbox`).** Postgres has no native TTL, so two `pg_cron` jobs run **hourly**: `DELETE FROM idempotency_keys WHERE expires_at < now()` and `DELETE FROM outbox WHERE published_at < now() - interval '1 day'`. Direction matters: the 7-day idempotency window is a **heuristic safety margin, not a hard business rule** (ADR-001/ADR-004: retries occur in seconds-to-minutes; replaying a `client_message_id` after 7 days is a client bug, out of scope). So a *late* sweep is harmless — keys simply live longer, giving *more* dedup coverage at the cost of table bloat; the sweep must never delete *earlier* than `expires_at`. The failure mode to guard is bloat, not correctness: alert on `COUNT(*) FROM idempotency_keys WHERE expires_at < now() - interval '1 hour'` (and the analogous `outbox` backlog) so a stalled `pg_cron` job is caught before the partial-index and PK lookups on the write path degrade. Note the prune `DELETE`s scan the full table (the partial index only covers *unpublished* `outbox` rows), so they are planned as periodic maintenance, not hot-path queries.

## Access-pattern parity (ADR-007 §4 → this schema)

| Access pattern | Store | Implementation | Consistency |
|---|---|---|---|
| Get messages after sequence | PG | `WHERE chat_id=$1 AND sequence>$2 ORDER BY sequence` | strong |
| Get recent N messages | PG | `WHERE chat_id=$1 ORDER BY sequence DESC LIMIT N` | strong |
| Get specific message | PG | `WHERE chat_id=$1 AND sequence=$2` | strong |
| Allocate sequence | PG | `UPDATE chat_counters … RETURNING seq` | strong |
| Idempotency check | PG | fast-path `SELECT` on PK, then claim | strong |
| Get delivery state (user,chat) | PG | PK lookup | strong |
| List delivery states for user | PG | `WHERE user_id=$1` (PK prefix) | strong |
| Update watermark (monotonic) | PG | `INSERT … ON CONFLICT DO UPDATE … WHERE` | strong |
| Get user by ID | FS | `get users/{id}` | strong |
| Find user by phone | FS | `where phone_number==` | strong |
| Get chat metadata | FS | `get chats/{id}` | strong |
| List chat members | FS | `where chat_id==` | strong |
| List user's chats | FS | `where user_id==` | strong |
| Check user in chat | FS | `get memberships/{chat}__{user}` | strong |
| Add / remove member | FS | `set` / `delete memberships/{…}` | N/A (write) |
| Validate session | FS | `get sessions/{id}` | strong |
| List user's sessions | FS | `where user_id==` | strong |
| Revoke session | FS | `delete sessions/{id}` | N/A (write) |
| Get pending OTP | FS | `get otp_requests/{phone_hash}` | strong |
| Issue OTP (conditional) | FS | transaction: read, write iff absent or past `expires_at` | strong |
| Consume OTP + register | FS | transaction: assert OTP, `create phone_index`, `create users`, `create sessions`, update OTP | strong |
| Claim a phone number | FS | `tx.Create phone_index/{phone_hash}` | N/A (write) |
| Find the direct chat for a pair | FS | `get direct_chats/{min}__{max}` | strong |
| Create a direct chat (unique per pair) | FS | transaction: read sentinel, then `create direct_chats`, `create chats`, `create memberships` ×2 | strong |
| Create a group chat | FS | transaction: `create chats`, `create memberships` ×N — no sentinel | strong |

Every ADR-007 pattern is preserved; several eventual-consistency reads become strong under the new stores. Four rows are ADR-015's auth patterns, added in v1.2, and the last three are ADR-016's chat-lifecycle patterns, added in v1.3 — neither set was in ADR-007 §4.

---

## Consequences

### Positive
- **Nothing from ADR-007 is lost**, and several reads gain strong consistency for free.
- **No manual secondary indexes** on either store — Firestore auto-indexes single fields; Postgres PKs serve the message/delivery patterns.
- **The write path is one transaction** end-to-end (counter + message + idempotency + outbox), which DynamoDB could not offer with a returned counter value.
- **Implementation-ready:** the DDL and the three load-bearing statements are copy-adaptable into the first migration + Ingest PR.

### Negative
- **One new sweeper:** `idempotency_keys` needs a `pg_cron` (or equivalent) job because Postgres lacks native row TTL — the single place TTL got harder (sessions got easier via Firestore TTL).
- **Cross-store integrity is on the application**, enumerated above; a bug there is not caught by a database constraint.
- **Chat creation now spans both stores** (v1.3): the chat, its memberships and the direct-pair sentinel are one Firestore transaction, while `chat_counters` is a Postgres row that cannot join it. ADR-016 §2.2 had all five items in a single `TransactWriteItems`; the polyglot split is what costs that, and the counter's lifecycle has to be designed for it rather than assumed (see the Firestore model).
- **`outbox` grows** until published rows are pruned; a periodic `DELETE FROM outbox WHERE published_at < now() - interval '1 day'` (or partition-drop) is required.

### Neutral
- `otp_requests` (ADR-015) is deferred to the identity tier with Firestore TTL; specified when auth is re-implemented — **done in v1.2**, together with `phone_index`.
- **`messages` long-term growth is unbounded and unaddressed in v1.** Postgres has no analogue to DynamoDB's 10 GB item-collection ceiling (ADR-007 §2.1), which is a relief, but a production `messages` table grows without limit. Range-partitioning by `created_at` (monthly) or hash-partitioning by `chat_id`, plus an archival/cold-storage policy, is the eventual answer — deferred exactly as ADR-007 deferred hot-partition mitigation to a future ADR. For the deploy-and-destroy lab it does not bite; it is named so it is not forgotten at scale.

| v1.3 | 2026-07-27 | **The direct-chat uniqueness sentinel, specified (M1.3 prerequisite). No decision changed — the decision was already made twice.** M1.3's headline invariant is *at most one direct chat per pair under concurrency*, and the Firestore model had no document that could enforce it. The mechanism was not an open question: **ADR-016 §2.1** decided a dedicated `direct_chat_index` keyed `{min}#{max}` → `chat_id` under a conditional put (rejecting a GSI on `chats` and a GSI on `chat_memberships` for reasons that still hold), and **ADR-006 §4.1** pinned the canonicalisation — member IDs sorted lexicographically so `{A,B}` and `{B,A}` map to one chat. What was missing was the substrate binding, which is this record's job, so **`direct_chats/{min}__{max}`** joins the Firestore model with `chat_id` + `created_at`, no TTL. The justification is `phone_index`'s verbatim: a Firestore transaction locks what it *reads*, a query matching nothing locks nothing, and the failure is not a mergeable duplicate but **two chat IDs for one conversation**, each accumulating its own sequence in Postgres while both clients believe they share a history. Four points settled rather than left to the implementation: the separator is **`__`** for consistency with `memberships`, since ADR-016's `#` rationale ("user IDs are ULIDs") no longer holds against UUIDs, whose alphabet excludes both characters; the sentinel is a **separate document, not a deterministic chat ID**, because a chat ID travels through URLs, Kafka partition keys and lake rows, and deriving it from the members would publish the membership everywhere the ID appears, unrotatably; **groups are out of scope** (identical membership does not make two groups the same chat); and the **race loser completes**, re-reading the sentinel for the winner's `chat_id` and returning `200 OK` per ADR-006 §4.1 — the opposite of the registration race, whose loser holds a consumed OTP (ADR-015 §10.2 as corrected in its v1.4). Two record defects fixed in passing: the collection table still said **ULID** for `users`/`chats`/`sessions` doc IDs and the membership doc-ID invariant still said **54 bytes**, both corrected to UUID/74 in v1.1's changelog but never in the body. One gap **opened rather than glossed**: ADR-016 §2.2's five-item transaction included `chat_counters {seq: 0}`, which a Firestore transaction cannot hold now that the counter is a Postgres row — chat creation straddles the stores, and M2.2 must decide the counter's lifecycle (a self-creating upsert on first use is the shape that avoids a second failure window). Three access patterns added to the parity table. |
